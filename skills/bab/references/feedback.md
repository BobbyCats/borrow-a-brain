# 反馈给作者

识别明确的纠正，不能根据情绪猜测“不满意”。同一任务同一问题的明确纠正可交给 `correction` 累计，达到 3 次后只建议一次。先修正本次问题。

用户愿意反馈时，整理最小必要内容：

1. 用户希望完成什么。
2. 希望得到什么、实际得到什么。
3. 可以重现问题的步骤。
4. 已观察到的证据。
5. 对原因的推测，明确标注“待验证”。
6. 建议改法。
7. Skill 与版本、宿主应用、系统、运行环境及安装方式。只填写本次问题需要且已知的字段，不收集账户名或机器标识。必要时附少量经过审阅的摘录。

调用 `feedback-draft` 只保存本地草稿。不要把完整历史附上。脚本会遮盖常见邮箱、电话、路径和凭据；它不是完备的脱敏系统。

向用户展示**实际接收地址、完整待发送正文、剩余身份线索**。用户明确说发送后，带同一个 `approvalHash` 调用 `feedback-send`。正文或地址有任何变化都重新预览。哈希证明确认的是哪份草稿，不是代替用户确认的权限凭证。

服务器未配置时，交付本地草稿，不能说已经反馈给作者。网络中断可能代表服务端收到但客户端没拿到回执，使用同一报告编号重试。

成功后保存私有查询回执。使用时由现有 `update-check` 按 [维护说明](maintenance.md) 顺带查询已发送报告；用户主动查询时使用 `feedback-status`。只用原接收地址和回执做 GET，不重新发送正文或查询未发送草稿。按返回的版本关系区分“作者标记修复”“已验证可下载”“本机已安装”，不能因为版本号变大就断言用户的问题已解决。

删除本地反馈草稿不会删除服务端已发送的副本。服务端删除要求作者单独处理。
