# 方法与更新机制 · 技术说明

借个脑子通过两条路径改进：用户积累自己的方法，作者根据反馈维护 Skill。方法库和发行代码分开保存，两者分别确认、分别更新。

本文供了解实现机制的读者与维护者查阅。日常安装和操作见[使用指南](quickstart.md)。

以下更新机制自 0.1.10 起适用。方法复用与更新检查的验证见 [0.1.10 验证记录](verification-0.1.10.md)。反馈跟进与失败重试沿用 [0.1.9 的实现](verification-feedback-update.md)。

## 个人方法如何积累

```text
完成当前任务 → 发现具体做法 → 查重与只读预览
→ 展示内容、边界、理由和范围 → 用户确认保存草稿
→ 新问题与范围外场景试用 → 用户确认启用 → 后续按任务选用
```

- **发现**由 AI 根据当前已读且获准的内容判断。具体纠正、反复采用的判断和明确认可的做法可以成为依据；普通点赞或只改字句不够。
- **提议**在完整交付之后，一次一项。用户看到“保存为草稿（附推荐理由）／修改后再存／这次不存”三个选项。没有回复不保存，拒绝后不在本会话重复追问同一项。
- **保存**由脚本核对预览内容与确认摘要。内容、范围或修订对象变化，需要重新预览。保存结果是草稿，不会进入自动选用目录。
- **启用**需要新问题和范围外场景的实际试用记录，再确认具体版本。用户已经明确授权“试用通过后启用”时，可沿用该授权。
- **修订**优先更新已有方法。有新证据或边界变化才增加版本；来源材料变化时，依赖旧来源的方法暂停自动选用，等待复核。

语义判断和试用质量依赖宿主模型。脚本检查状态与内容是否一致，不能替用户作出同意，也不能凭记录证明试用一定有效。确认得到的方法只代表基于有限材料的提炼，不代表完整复刻一个人。

实现入口：[发现流程](../skills/bab/references/discovery.md)、[档案状态](../skills/bab/references/people.md)、[收录与启用实现](../skills/bab/scripts/profiles.mjs)。

## 一条反馈如何进入新版本

| 阶段 | AI 或程序负责 | 用户或作者负责 |
| --- | --- | --- |
| 发现问题 | 先修正当前任务；同任务、同问题累计三次明确纠正后可建议反馈 | 用户也可以直接提出反馈 |
| 整理草稿 | 写明目标、预期、实际、复现步骤、证据和待验证原因 | 用户核对完整正文与实际接收地址 |
| 发送 | 对照确认摘要发送，保存私有回执；不自动附上完整聊天 | 用户明确同意发送 |
| 处理 | 后台保存状态、回复、修复版本和审计记录 | 作者复现、判断原因、修复并测试 |
| 发布 | 组装器生成签名包；网站构建检查分发一致性 | 作者发布正式包、更新官网并填写修复版本 |
| 跟进与验收 | 使用时按私有回执查询已发送报告，只提示状态、回复或版本关系的变化 | 用户同意更新，并重试原问题 |

当前没有“收到反馈就自动修改代码”的流程。客户端分别说明作者标注的修复版本、已经验签的可用版本和本机版本。尚未取得可信更新时，不把作者标注说成“可安装”；安装后也需要用户重试原问题。

纠正计数需由模型调用命令，按同一个任务与问题累计。该计数与方法收录分开，不能用反馈阈值限制主动收录。

实现入口：[反馈说明](../skills/bab/references/feedback.md)、[客户端](../skills/bab/scripts/feedback.mjs)、[作者后台](../server/console.mjs)。服务与发布操作见 [作者维护与分发](author-operations.md)。

## 更新什么时候发生

1. AI 使用本套件时运行 `update-check`，自动读取当前安装版本和已有更新配置。每份安装成功检查后间隔 7 天；失败后依次等待 1 小时、6 小时、24 小时，后续失败保持 24 小时。到期后再次使用才重试，成功后恢复七天间隔。版本或可信配置变化会重新检查，手动检查可以强制执行。
2. 客户端验证签名，返回新版本与说明。同一可用版本只自动提醒一次；失败时继续当前任务。同一次调用还会检查已发送反馈，成功间隔 24 小时，一次最多查 3 条。反馈与版本检查各自计时，互不阻塞到期判断；没有更新源也可以查询反馈。
3. AI 展示变化和影响。用户同意具体版本后，客户端再检查签名、内容、路径和本地改动，更新代码。
4. 保留独立数据目录与用户配置，说明本次变化，并按宿主要求重新加载。

这里没有常驻进程，也不会重新上传反馈正文。检查间隔不是通知期限。提醒去重在命令返回时记录，尚无用户实际看到提醒的回执。不同安装共用报告快照，各自判断是否需要更新或复测，避免交替使用时重复提醒。

客户端支持多个 HTTPS 更新源，但官方安装包只配置了 `jclab.work` 一个源。国内官网下载不依赖 GitHub；这不等于已经部署独立备用镜像。

实现入口：[更新约定](../skills/bab/references/maintenance.md)、[检查与安装实现](../skills/bab/scripts/update.mjs)。

## 当前达到的范围

- **方法积累**已有端到端实现和部分真实对话验证。参考模型通过已测的自动复用、正文后收录和确认边界场景；Luna 仍有首次应用和触发过重等差异。
- **版本更新**已验证签名分发、新安装和旧客户端升级，个人资料与配置保留。
- **反馈处理**已有草稿、确认发送、私有后台和回执查询。0.1.9 在使用时跟进已发送报告，并核对修复版本。
- **作者发布**已有组装和校验工具。正式包上传、官网发布与分发元数据切换仍需协调，静态网站部署不包含安装包上传。

对应证据见 [0.1.8 验证记录](verification-0.1.8.md) 与 [反馈服务历史验收](verification.md)。程序测试不证明所有模型都会主动调用相应命令，也不代替普通新手的使用验收。

0.1.10 减少普通任务的重复读取，并让更新检查自动取得所需配置和版本。方法保存、启用和更新安装继续使用原有确认流程。
