第一阶段只改展示约定。默认在同一条最终回复中依次交付正文、方法卡、三个文字选项。三个选项为“保存为草稿（推荐）”“修改后再存”“这次不存”；推荐项紧接具体理由。原生问题卡只有在宿主能保证其展示晚于成品、且工具用途允许时才使用。质量检查引用这条规则，避免复制另一套判定。

第二阶段保留第一阶段，再改善 `help profile-intake`。帮助返回包内已有示例组成的完整预览参数，说明边界为字符串、来源日期必填、scope 是 JSON 字段。示例没有保存授权；未试用不标通过。没有新建第二份字段校验实现。

B 版入口触发规则保持不变。发现说明从“确认后才落库”起的内容逐字保留；保存、摘要确认、试用、启用和持久化实现均未修改。

正常安装器已将修复同步到用户级安装。安装源沿用原正式包的作者配置与可信公钥，只覆盖本次四份文件。47 个安装文件与本地修复包一致。

真实数据核对：两份既有方法仍为 v0002 启用；全部资料文件不变。状态文件仅安装回执变化，其余字段完全一致。全局 AGENTS、作者配置和可信更新公钥均保持不变。留有安装前备份。

GPT-6 Luna / max 的实际 Desktop 新会话使用本机安装与隔离合成库。第一段 6 轮：

- 不点名加载 bab。第二轮正确改稿，正文后展示候选、项目范围、理由和三个选项。
- 第二轮执行档案与记忆查重，却跳过只读预览。候选状态仍被声明为“未选用”，未准确标为“候选建议，未入库”。因此不是完整验收通过。
- “可以，再短一点”不保存；明确拒绝不重提。第二轮至第四轮库哈希相同。
- 第一轮有空方法分工的 route-save；这是分工记录，不是方法保存，不能将整段描述为零写入。
- 第四轮后由评测者通过正式接口添加明确标注的人工方法夹具。第五、六轮切换业务任务时，模型沿用了旧空目录，没有选用已存在的 v0002。未加载方法即判复用失败，不能以文案正确代替调用证据。
- 夹具包含相关启用 v0002、旧版、同义草稿、无关启用方法和另一项目方法。它们是人为预置的测试状态，不是真实人物方法或试用成果。模型没有保存或启用这些夹具。

为区分新会话加载与同会话目录缓存问题，另开 Luna/max 新会话复测相同协作消息，共 2 轮。方法库在开聊前已存在；业务输入中没有命令、方法名称或预期选项。新会话按项目范围查目录、记录分工，读取相关方法的精确 v0002；版本选择通过。首次成品将锁定机器时间的原因放在两个安排之前，只部分执行了方法顺序。第二轮正确沿用并在纠正后完整体现顺序，无重复收录。这些结果不覆盖前述换任务失败。

新会话首次 route-load 的范围多了一个空格，返回 not-found，修正后成功；不能因命令退出码为零而算首次成功。两轮执行时长分别为 110.017 秒和 5.964 秒。方法与记忆未变，仅分工记录和临时路由参数变化。两个 Desktop 会话共 8 轮，均从运行元数据核对为 gpt-6-luna / max。

展示顺序依据公开消息和工具事件核对，没有另做截图视觉验收。Luna 候选还把“避免把意向写成承诺”概括为“只有负责人和期限齐全才列待办”，其对无截止日期的明确承诺是否适用未验证；该候选没有保存。
