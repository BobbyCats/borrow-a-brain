# 范围判断位置对照

2026-10-11。结论：候选未达到预先设定的采用门槛，未合并规则，未更新本机，未发布。

## 单一变量与门槛

基线是当前 0.1.7 加本地预览及任务级目录修复。候选仅将 routing.md 现有 context 段移到“两层选择”之前。段落逐字不变，文件仍为 47 行、6152 个 UTF-8 字节，其余 46 个 Skill 文件相同。业务输入、夹具配方、运行代码和每个模型的设置保持一致。

参考模型 gpt-6.1-sol / medium 执行 6 段、20 轮。补充模型 gpt-6-luna / max 执行 10 段、36 轮。使用真实 Codex app-server 的隔离新上下文、合成资料和固定的 A/B 顺序；重复场景反转 A/B 次序。没有行为失败重抽或替换样本。

开始运行前冻结采用门：参考模型的范围、精确版本、首次方法应用和确认边界不得出现新增失败。若参考模型持平，Luna 至少两个配对改善，且须分别覆盖会议收录和换任务复用；不得出现父版正确、候选反而错误的范围反转。个人事务反例也必须通过。这个门用于小样本工程选择，不是统计显著性检验。

判分检查整段对话里实际执行的数据命令。调用 context 本身不等于范围正确；先查错再修正不算首次通过。个人事务允许探测 context 元数据，但查询和收录须保持 personal。独立审查先锁定匿名评分，再解盲。

参考模型两版都完成真实预览、正文后方法卡、三个选项以及模糊认可和拒绝不保存。换任务时重新查目录，读取正确 v0002，首稿体现方法顺序。该组本批持平，不能由每场景一个样本证明普遍等效。

Luna 的会议范围有改善信号；换任务的四段均执行了重查，但仍查询 personal，漏掉项目 v0002。四段都成功读取过包含范围段落的 routing.md，因此不是仅凭“没有读到说明”即可解释。第二次重复的两版还因范围错而再次提出项目已有的同义方法，均未保存。

Luna 另有原有的收录质量缺口：部分样本漏查相关记忆，推荐项没有紧邻具体收益，候选对承诺的条件概括过度，以及调用声明或临时参数位置不符合现有约定。这些分别保留，不以范围改善抵消，也未在本轮追加规则。

全部 16 段、56 轮完成。受试者未修改规则；未未经确认保存或启用方法。参考模型的复用段只有正常 tasks 分工变化；Luna 的受试期间资料均未变化。中途方法夹具由评测者通过原接口预置，不算受试者自主保存。

## 决定与保留项

改善仅发生在会议场景，没有覆盖换任务复用，故未达到冻结的采用门。候选留在实验目录，当前仓库 Skill 和本机安装保持基线。真实资料、配置、完整全局规则及全部 47 个安装文件的前后哈希一致。

这次结果不支持“只把范围说明前移就足以解决范围选择”。下一项值得验证的假设是：将现有 context 与 route-catalog 说明合并进同一个执行步骤，先从宿主项目取得范围，再处理用户明确指定的个人范围，最后查询目录。删除原处重复说明，保持单一流程。该假设本轮未实施，也未被验证为有效。

无需据此重跑整套 A–E 消融。下一轮继续使用这三类输入，分别验证范围、精确版本和实际应用即可。本轮没有运行发行检查，没有推送、发布或部署。
